## Create an OTLP data stream

**Goal:** an OTLP data stream with a destination table for each signal.

1. Navigate to **Storage > Data Streams** and click **Create Data Stream**.
2. Select **OpenTelemetry (OTLP)** as the source type.
3. Name the data stream (e.g., "production-telemetry"). The destination table names are filled automatically.
4. Click **Create**.

**Result:** The app sets up a destination table per signal (logs, metrics, traces) with a default column mapping, so there is nothing to map by hand before you start sending data.

## Configure your application

**Goal:** your SDK or collector exports telemetry to the stream.

1. Open the OTLP source detail page. It provides:
   {/* VERIFY(Nikita): the step does not say how to reach the source detail page. Check the click path from Storage > Data Streams and add it. */}
   - **Endpoint URL** with a one-click copy button.
   - **Environment variable snippet** ready to paste into your application or deployment configuration.
   - **Table statistics** for each destination table (logs, metrics, traces), showing waiting vs. imported data.
   - **Import conditions** — the same configurable thresholds (interval, data size, record count) as HTTP data streams. [Learn more](/storage/data-streams/reference/#conditions)
2. To connect any OpenTelemetry SDK or collector, set two environment variables:

   ```bash
   export OTEL_EXPORTER_OTLP_ENDPOINT="<your-stream-endpoint>"
   export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
   ```

   Replace `<your-stream-endpoint>` with the endpoint URL shown on the source detail page.
3. Install the exporter and run your application, or add the exporter to your collector. The OTLP/HTTP endpoint is compatible with any OpenTelemetry SDK or collector. Below are quick-start snippets for popular languages and the OpenTelemetry Collector.

:::caution[Don't append the signal path yourself]
The endpoint URL is a **base** URL. The SDK appends `/v1/logs`, `/v1/metrics`, or `/v1/traces` to it automatically, based on the signal it is exporting. Setting `OTEL_EXPORTER_OTLP_ENDPOINT` to a URL that already ends in `/v1/traces` breaks the export — most exporters either reject the value or silently strip the suffix. Use the per-signal `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` variables only if you need to override a single signal, and give those the full signal path.
:::

**Result:** Once these variables are set, any official OpenTelemetry SDK will automatically pick them up and begin exporting telemetry data to your Keboola project.

## Keep the secret out of your logs

**Goal:** the source's secret travels in a request header and stays out of URLs.

The endpoint URL shown in the app embeds the source's 48-character secret as its last path segment. That is convenient — a single string configures any SDK — but URLs end up in access logs, CDN logs, and APM traces.

The API therefore returns the same endpoint in two forms in the source detail (`GET /v1/branches/{branchId}/sources/{sourceId}`):

{/* VERIFY(Nikita): the call is given without a host or an auth header. Check both (the tutorial uses the Stream API host and X-StorageApi-Token) and add a full request. */}

| Field | Value | How to authenticate |
|---|---|---|
| `otlp.url` | `https://stream-in.keboola.com/otlp/<projectId>/<sourceId>/<secret>` | Secret in the URL — nothing else needed |
| `otlp.baseUrl` + `otlp.secret` | `https://stream-in.keboola.com/otlp/<projectId>/<sourceId>` | `Authorization: Bearer <secret>` header |

For anything beyond a quick test, prefer the header form:

1. Read `otlp.baseUrl` and `otlp.secret` from the source detail.
2. Set the endpoint to the base URL and pass the secret in a header:

   ```bash
   export OTEL_EXPORTER_OTLP_ENDPOINT="<otlp.baseUrl>"
   export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
   export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer <otlp.secret>"
   ```

3. If your exporter sends a malformed `Authorization` header, percent-encode the space: `Authorization=Bearer%20<otlp.secret>`. `OTEL_EXPORTER_OTLP_HEADERS` values are specified as W3C Baggage, and SDKs differ in how strictly they decode them.

**Result:** Both forms accept exactly the same traffic. Note that an HTTP source's secret cannot be used against the OTLP endpoints, or vice versa — secrets are scoped to the transport.

## Verify data ingestion

**Goal:** confirm that telemetry reaches Storage.

1. Wait until the stream's [import conditions](/storage/data-streams/reference/#conditions) are met (by default within about a minute). Records become available in Storage once they are.
2. Check the **Table statistics** on the source detail page to confirm data is flowing.

{/* VERIFY(Nikita): "within about a minute" against the reference defaults, a 30-second upload to staging followed by a 1-minute import interval. Check the delay a reader should expect. */}

**Result:** **Table statistics** shows imported data for the destination tables. For the fields each table can hold and for query examples, see the [OpenTelemetry reference](/storage/data-streams/opentelemetry/reference/).
