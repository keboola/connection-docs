## Phases and tasks

<FlowStrip steps="Every day at 06:00, Europe/Prague, the schedule starts the flow|Phase 1: both HTTP connectors, at the same time|Phase 2: the transformation, which needs both tables|Phase 3: redeploy the app, which reads that table" label="The flow this page builds" />

- **Tasks inside one phase run in parallel.** A task is a configuration to run, a notification to
  send, or a variable to set.
- **Phases run one after another**, and the flow moves on only when a phase is finished. Things
  that can happen at the same time share a phase; things that depend on each other get their own.
- If you took the [spreadsheet side trip](/getting-started/write/), its destination goes in phase
  3 too, for the same reason as the app.

<details>
<summary>Adding tasks and phases by hand, and what else a flow can do</summary>

To add a second task to a phase that already has one, hover the phase and click the **+** in the
small toolbar that appears on its top edge. It opens an **Add Task** menu scoped to that phase
(**Component**, **Notification**, **Variable**). The **+** on the line *between* phases opens a
longer one that also offers **Conditions**, because a condition sits between phases rather than
inside one. Do not confuse it with the **+** *below* a phase, which starts a new phase instead.
That toolbar belongs to the phase; the one that appears on the card itself is the task's, and
carries **Run task** and its settings.

Inside the sales configuration the five files are already fetched by one job. Row-based components
like this one can be [parallelized internally](/flows/#execute-tasks-in-parallel), and in **Jobs**
you will see that one task fan out into a job per row.

Flows can also branch on what happened: retry a task, take a different path on failure, end early.
That is [conditions](/flows/#conditions), and you need none of it yet.

</details>

## Set it up

<Tabs syncKey="howto">
<TabItem label="Prompt">

Open **Kai Agent** in the top bar and ask for the whole flow; assembling configurations you already
have is a documented Kai job ([Complex Workflows](/kai/use-cases/#complex-workflows)). The Flows
section has Kai wired in too: **Create Flow** opens with a prompt field, and a flow that already
has tasks offers **Modify with Kai** in its header.

```text title="Prompt" wrap
Create a flow called "Boolabean morning outlook" with three phases, in this order:
1. Phase 1 runs the two HTTP data source configurations "Boolabean sales" and "Boolabean forecast" in parallel.
2. Phase 2 runs the transformation "Boolabean staffing outlook".
3. Phase 3 redeploys the data app "Staffing Outlook Grid" so it shows the new table.

Then give the flow a schedule: every day at 06:00 Europe/Prague. Then run the flow once now and tell me whether every phase succeeded and how long the run took.
```

**Expect three approvals:** the flow, the schedule, the run. Use your app's own name in the third
phase, leave the phase out if you skipped the app, and add
`and the "Boolabean outlook to Sheets" destination` to it if you took the spreadsheet side trip.

**Check:** the canvas shows **three separate phases**, with the two connectors side by side in the
first. If it came out as one phase, switch to the **UI** tab, where the **+** below a phase starts a
new phase, and move the later tasks there. The flow's **Schedules** tab shows the schedule Kai set,
with its timezone and a toggle to pause it.

**Notifications** are still yours: two clicks in the flow's own tab below, and the part people
forget exists.

</TabItem>

<TabItem label="CLI / API">

A flow is a configuration like any other, and `kbagent` writes it from a YAML file. Run `kbagent flow schema`
once to see the full format with comments (add `--project <alias> --full` for the live JSON
schema); the file below is the three phases of this guide.

```yaml title="flow.yaml"
phases:
  - id: "extract"
    name: "Extract source data"
    next:
      - id: "default"
        goto: "transform"
  - id: "transform"
    name: "Build staffing outlook"
    next:
      - id: "default"
        goto: "redeploy"
  - id: "redeploy"
    name: "Redeploy data app"
    next:
      - id: "done"
        goto: null
tasks:
  - id: "task-sales"
    name: "Boolabean sales"
    phase: "extract"
    enabled: true
    task: { type: job, componentId: "keboola.ex-http", configId: "<sales-config-id>", mode: run }
  - id: "task-forecast"
    name: "Boolabean forecast"
    phase: "extract"
    enabled: true
    task: { type: job, componentId: "keboola.ex-http", configId: "<forecast-config-id>", mode: run }
  - id: "task-outlook"
    name: "Boolabean staffing outlook"
    phase: "transform"
    enabled: true
    task: { type: job, componentId: "keboola.snowflake-transformation", configId: "<transformation-config-id>", mode: run }
  - id: "task-app"
    name: "Staffing Outlook Grid"
    phase: "redeploy"
    enabled: true
    task: { type: job, componentId: "keboola.data-apps", configId: "<app-config-id>", mode: run }
```

Two tasks in one phase is the parallelism: both connectors sit in `extract`, and the phase is done
when both are. `goto: null` ends the flow. On a BigQuery project the transformation's
`componentId` is `keboola.google-bigquery-transformation`. Without the app, delete the `redeploy`
phase and the `task-app` task, and set the `transform` phase's `goto` to `null`.

**Where the four IDs come from.** The three `configId` values for the connectors and the
transformation were printed when you created them; `kbagent config list --project docs-demo
--component-id keboola.ex-http` finds them again. The app's is the one identifier that is not the
number you have been using: `kbagent data-app detail --project docs-demo --app-id <app-id>` prints
the Storage configuration ID, and that is what a flow task takes.

Check the file before it reaches the project, then create it:

```bash
kbagent flow validate --project docs-demo --file @flow.yaml
```

```bash
kbagent flow new --project docs-demo --name "Boolabean morning outlook" --file @flow.yaml
```

It prints the flow's configuration ID, which the next two commands take as `<flow-id>`;
`kbagent config list --project docs-demo --component-id keboola.flow` finds it again.

**The schedule** is a separate configuration, and one command upserts it:

```bash
kbagent flow schedule --project docs-demo --flow-id <flow-id> --cron '0 6 * * *' --timezone Europe/Prague --enabled
```

**Run it now** rather than waiting for six in the morning:

```bash
kbagent job run --project docs-demo --component-id keboola.flow --config-id <flow-id> --wait
```

**Check:** the run's own job and one job per task:

```bash
kbagent job list --project docs-demo --component-id keboola.flow --limit 5
```

Notifications have no command; they live in the flow's **Notifications** tab, below.

<details>
<summary>Clicking a task opens its settings</summary>

Selecting a task gives you **Edit Configuration**, **Run rows** (for row-based components like
your HTTP connector, so a flow can run a subset of rows), **Retry After Failure**, **Delay Before
Start**, and **Continue on Failure**, which reads *Handled via Conditions*, because in Conditional
Flows that behaviour comes from [conditions](/flows/#conditions) rather than a toggle.

</details>

<details>
<summary>If you took the connector side trips</summary>

If you also added the Google Sheets or database connector, put them in the first phase alongside
the two HTTP configurations; that is the same parallelism, with a third source. Then make the
transformation read from the tables those connectors produce, since they land in their own
buckets: on a hand-built transformation, repoint its **input mapping**; on a Kai-built one there
is no input mapping, so re-prompt Kai to include the new tables. A flow that runs the right
components against the wrong inputs succeeds and produces nothing useful.

</details>

## Run it

*Coming from the **Prompt** or **CLI / API** tab? The run already happened (the prompt asked for
it, `job run --wait` did it) and the schedule is set. Read on for notifications.*

- If **Run flow** is disabled, the Builder is still holding your changes as a draft: click **Save**
  first, however the flow got built, Kai included.
- Click **Run flow** and confirm with **Run**. A notification with a **Show job** link appears,
  and while the run is in progress the header offers **Terminate flow**.
- **Jobs** shows which step failed, because every task creates its own job; the flow's **All Runs**
  tab shows each run with its phases.
- Expect the loads to take a couple of minutes and the transformation under one; the app phase is
  slowest, because a deploy builds and starts a container.

## Set a schedule

*Coming from the **Prompt** or **CLI / API** tab? The schedule is already there; open the tab to
see it, and skip to notifications.*

Open the flow's **Schedules** tab and click **Create Schedule**. For a fixed hour use **Set Your
Own** and set 06:00, before the first café opens, then click **Set Up Schedule**.

![Screenshot - Create a schedule](/getting-started/automate/06-create-schedule.png)

![Screenshot - The schedule](/getting-started/automate/07-schedule-set.png)

- **Check the timezone the list displays.** A schedule set by hand may show in UTC, and 06:00 UTC
  is 08:00 in Prague in summer.
- **The toggle pauses it** without deleting it.

<details>
<summary>Other intervals, several schedules, and table triggers</summary>

The predefined intervals are **Every 15 minutes**, **Every hour**, **Once a day**, **Once a week**
and **End of month**; **Set Your Own** covers every day, week or month at an hour and minute you
pick. A flow can hold **several** schedules: they work independently, the flow runs whenever any
of them fires, and the tab shows a count. If you share a stack with other projects, scheduling
slightly off the hour avoids the busiest moments. A schedule can also be driven by a table changing
rather than a clock; see [Schedule and Automate](/flows/#schedule-and-automate).

</details>

## Get told when it breaks

A pipeline that fails silently is worse than a manual one. Open the flow's **Notifications** tab and
edit it in place; there are three cards:

| Card | Fires when |
|---|---|
| **Success** | the flow finishes successfully |
| **Errors** | the flow finishes with an error |
| **Processing** | the job runs longer than usual, by a percentage you set |

Each takes **Email** addresses (pick colleagues or type any address) or a **Webhook** URL. Fill in
**Errors** at minimum.

![Screenshot - Notifications](/getting-started/automate/08-notifications.png)

<details>
<summary>Different alerts for different failures</summary>

There is a second, finer mechanism: a **Notification** task placed inside the flow, driven by a
[condition](/flows/#conditions) such as *if any task in the flow ended with an error*. That is
what you reach for when one flow needs different alerts for different failures; these three cards
are enough here.

</details>

## Check it worked

- The **Schedules** tab shows a count, and the flow's **All Runs** tab a run: your name against a
  manual run, `Schedule for <flow ID> Scheduler` against an automatic one.
- **A red run can still have done most of its work:** when the app phase fails, the data phases
  before it have already rebuilt `staffing_outlook`. [Check it worked](/getting-started/check/) shows
  how to read the run.
- Tomorrow morning there will be a second run you did not start, on a forecast that has moved by a
  day.
