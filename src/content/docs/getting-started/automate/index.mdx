## Phases and tasks

<FlowStrip steps="Every Monday at 06:00, Europe/Prague, the schedule starts the flow|Phase 1: both HTTP connectors, at the same time|Phase 2: the transformation, which needs both tables" label="The flow this page builds" />

- **Configurations in one phase run in parallel.** A task can also send a notification or set a
  variable; those run first, one after another.
  {/* keboola.flow configurationSchema, public /v2/storage component index, read 2026-10-01:
  "Within each phase, tasks execute in this order: notification tasks first (sequentially), then
  variable tasks (sequentially), finally job tasks (in parallel)." flows/index.md says every task
  in a phase runs in parallel (MISSING.md). */}
- **Phases run one after another**, and the flow moves on only when a phase is finished. Things
  that can happen at the same time share a phase; things that depend on each other get their own.
- **The app is not in the flow.** Ours reads `staffing_outlook` each time someone opens it, so it
  shows whatever the last run wrote; the **Prompt** tab of
  [Build an app](/getting-started/app/) has the question that checks yours.
- If you took the [spreadsheet side trip](/getting-started/write/), its destination goes in a third
  phase: it sends the table, so it runs after the transformation.

<details>
<summary>Adding tasks and phases by hand, and what else a flow can do</summary>

To add a second task to a phase that already has one, hover the phase and click the **+** in the
small toolbar that appears on its top edge. It opens an **Add Task** menu scoped to that phase
(**Component**, **Notification**, **Variable**). The **+** on the line *between* phases opens a
longer one that also offers **Conditions**, because a condition sits between phases rather than
inside one. Do not confuse it with the **+** *below* a phase, which starts a new phase instead.
That toolbar belongs to the phase; the one that appears on the card itself is the task's, and
carries **Run task** and its settings.

Inside the sales configuration the five files are already fetched by one task. Row-based components
like this one can be [parallelized internally](/flows/#execute-tasks-in-parallel), and in **Jobs**
you will see that one task fan out into a job per row.

Flows can also branch on what happened: retry a task, take a different path on failure, end early.
That is [conditions](/flows/#conditions), and you need none of it yet.

</details>

## Set it up

<TabItem label="Prompt">

Open **Kai Agent** in the top bar and ask for the whole flow; in our runs Kai built it from the configurations already
in the project. [Complex Workflows](/kai/use-cases/#complex-workflows) shows the bigger pipelines
it builds from scratch. The Flows section has Kai wired in too: **Create Flow** opens with a prompt field, and a flow that already

```text title="Prompt" wrap
Create a flow called "Boolabean morning outlook" with two phases, in this order:
1. Phase 1 runs the two HTTP data source configurations "Boolabean sales" and "Boolabean forecast" in parallel.
2. Phase 2 runs the transformation "Boolabean staffing outlook".

Then give the flow a schedule: every Monday at 06:00 Europe/Prague. Then run the flow once now and tell me whether every phase succeeded and how long the run took.
```

**Expect three approvals:** the flow, the schedule, the run. If you took the spreadsheet side trip,
change "two phases" to "three phases" and add a third line: `3. Phase 3 runs the data destination

<TabItem label="CLI / API">

A flow is a configuration like any other, and `kbagent` writes it from a YAML file. Run `kbagent flow schema`
once to see the full format with comments (add `--project <alias> --full` for the live JSON
schema); the file below is the two phases of this guide.

```yaml title="flow.yaml"
phases:
  - id: "extract"
    name: "Extract data"
    next:
      - id: "default"
        goto: "transform"
  - id: "transform"
    name: "Staffing outlook"
    next:
      - id: "done"
        goto: null
tasks:
  - id: "task-sales"
    name: "Boolabean sales"
    phase: "extract"
    enabled: true
    task: { type: job, componentId: "keboola.ex-http", configId: "<sales-config-id>", mode: run }
  - id: "task-forecast"
    name: "Boolabean forecast"
    phase: "extract"
    enabled: true
    task: { type: job, componentId: "keboola.ex-http", configId: "<forecast-config-id>", mode: run }
  - id: "task-outlook"
    name: "Boolabean staffing outlook"
    phase: "transform"
    enabled: true
    task: { type: job, componentId: "keboola.google-bigquery-transformation", configId: "<transformation-config-id>", mode: run }
```

Two tasks in one phase is the parallelism: both connectors sit in `extract`, and the phase is done
when both are. `goto: null` ends the flow. On a Snowflake project the transformation's
`componentId` is `keboola.snowflake-transformation`. With the spreadsheet side trip, add a third
phase the same way, with a task for `keboola.wr-google-sheets` and its configuration ID, and point
the `transform` phase's `goto` at it.

**Where the three IDs come from.** The `configId` values for the connectors and the transformation
were printed when you created them. `kbagent config list --project docs-demo --component-id
keboola.ex-http` finds the two connectors again, and the same command with the transformation's
`componentId` finds the transformation.

Check the file before it reaches the project, then create it:

```bash
kbagent flow validate --project docs-demo --file @flow.yaml
```

```bash
kbagent flow new --project docs-demo --name "Boolabean morning outlook" --file @flow.yaml
```

It prints the flow's configuration ID, which the next two commands take as `<flow-id>`;
`kbagent config list --project docs-demo --component-id keboola.flow` finds it again.

**The schedule** is a separate configuration, and one command upserts it:

```bash
kbagent flow schedule --project docs-demo --flow-id <flow-id> --cron '0 6 * * 1' --timezone Europe/Prague --enabled
```

**Run it now** rather than waiting for Monday morning:

```bash
kbagent job run --project docs-demo --component-id keboola.flow --config-id <flow-id> --wait
```

**Check:** the run's own job and one job per task:

```bash
kbagent job list --project docs-demo --component-id keboola.flow --limit 5
```

Notifications have no command; they live in the flow's **Notifications** tab, below.

<summary>Clicking a task opens its settings</summary>

Selecting a task gives you **Edit Configuration**, **Run rows** (for row-based components like
your HTTP connector, so a flow can run a subset of rows), **Retry After Failure**, **Delay Before

<details>
<summary>If you took the connector side trips</summary>

If you also loaded data from [Google Sheets](/getting-started/load/googlesheets/) or
[a database](/getting-started/load/database/), put those data source configurations in the first
phase alongside the two HTTP ones; that is the same parallelism, with a third source. Then make the
transformation read from the tables those connectors produce, since they land in their own
buckets: on a hand-built transformation, repoint its **input mapping**; on a Kai-built one there
is no input mapping, so re-prompt Kai to include the new tables. A flow that runs the right
components against the wrong inputs succeeds and produces nothing useful.

</details>

## Run it

*Coming from the **Prompt** or **CLI / API** tab? The run already happened (the prompt asked for
it, `job run --wait` did it) and the schedule is set. Read on for notifications.*

- If **Run flow** is disabled, the Builder is still holding your changes as a draft: click **Save**
  first, however the flow got built, Kai included.
- Click **Run flow** and confirm with **Run**. A notification with a **Show job** link appears,
  and while the run is in progress the header offers **Terminate flow**.
- **Jobs** shows which step failed, because every task creates its own job; the flow's **All Runs**
  tab shows each run with its phases, and [Reading a flow run](/getting-started/check/#reading-a-flow-run)
  says how long ours took.

## Set a schedule

*Coming from the **Prompt** or **CLI / API** tab? The schedule is already there; open the tab to
see it, and skip to notifications.*

Open the flow's **Schedules** tab and click **Create Schedule**. Under **Set Your Own**, set
**Every** to **Week**, **on** to **Monday** and **at** to `06` : `00`, before the first café opens.
The dialog starts in UTC: next to **Timezone**, click **UTC** and pick your own zone (**My
Timezone** heads the list), check the **Schedule Preview**, then click **Set Up Schedule**.

![Screenshot - The Create Schedule dialog set to every week on Monday at 06:00 with the time zone Europe/Prague, and a preview listing the next five Mondays at 06:00](/getting-started/automate/06-create-schedule.png)

![Screenshot - The flow's Schedules tab with one Date and Time schedule, At 06:00, only on Monday (Europe/Prague), and its toggle switched on](/getting-started/automate/07-schedule-set.png)

- **Mind the time zone.** Left on UTC, 06:00 is 08:00 in Prague in summer.
- **The toggle pauses it** without deleting it.

<details>
<summary>Other intervals, several schedules, and table triggers</summary>

The predefined intervals are **Every 15 minutes**, **Every hour**, **Once a day**, **Once a week**
and **End of month**; **Set Your Own** covers every hour, day, week, month or year, at the hours and
minutes you pick. A flow can hold **several** schedules: they work independently, the flow runs whenever any
of them fires, and the tab shows a count. If you share a stack with other projects, scheduling
slightly off the hour avoids the busiest moments. A schedule can also be driven by a table changing
rather than a clock; see [Schedule and Automate](/flows/#schedule-and-automate).

</details>

## Set up notifications

A pipeline that fails silently is worse than a manual one. Open the flow's **Notifications** tab and
edit it in place; there are three cards:

| Card | Fires when |
|---|---|
| **Success** | the flow finishes successfully |
| **Errors** | the flow finishes with an error |
| **Processing** | the job runs longer than usual, by a percentage you set |

Each takes **Email** addresses (pick colleagues or type any address) or a **Webhook** URL. Fill in
**Errors** at minimum.

![Screenshot - The flow's Notifications tab with its three cards, Success, Errors and Processing, each with Email and Webhook tabs and no recipients yet](/getting-started/automate/08-notifications.png)

<details>
<summary>Different alerts for different failures</summary>

There is a second, finer mechanism: a **Notification** task placed inside the flow, driven by a
[condition](/flows/#conditions) such as *if any task in the flow ended with an error*. That is
what you reach for when one flow needs different alerts for different failures; these three cards
are enough here.

</details>

- The **Schedules** tab shows a count, and the flow's **All Runs** tab a run: your name against a
  manual run, `Schedule for <flow ID> Scheduler` against an automatic one.
- **A red run can still have done most of its work:**
  [Reading a flow run](/getting-started/check/#reading-a-flow-run) says how to tell, and has the
  prompt that makes Kai read the run for you.
  {/* The prompt and its 2026-10-07 run note are on check/ since 2026-10-09 (one copy). */}
- Next Monday there will be a second run you did not start, on a forecast that has moved by a
  week.

:::note[What the weekly run costs, and how to stop it]
Only the jobs that do the work count as runtime: the five file jobs, the forecast and the
transformation, not the flow's own job or the containers that only hold others, and not the time
a job waits to start ([Pay As You Go](/management/payg-project/),
[job types](/extend/jobs/#job-type)). They came to about 4 minutes in our run
([Reading a flow run](/getting-started/check/#reading-a-flow-run)) and 2½ in an earlier one. Once a week that is 10 to 20 minutes a month; every day it
would be 75 or more. The Free Plan's allowance is up to 60 minutes a month, capped at what the
project used the month before, so a month that needs more than the one before, such as one with
five Mondays, can run short.

We could not confirm whether the app's own running time counts against the minutes. If it does, each day someone opens the app adds at least 15 minutes, because it runs
until **Auto Sleep** stops it, and one look a week comes to 60 to 75 minutes a month.

To pause the run, switch off the toggle on the flow's **Schedules** tab. To stop it for good,
point at the schedule's row and click **Delete Schedule**, then delete the flow with **Delete
flow** in its **⋯** menu; the configurations it ran stay.
:::
