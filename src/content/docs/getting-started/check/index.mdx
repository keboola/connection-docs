## What you should have

| What you built | What it does | Where it lives |
|---|---|---|
| Two HTTP configurations | bring the five files and the live forecast into the project | **Components** |
| SQL transformation | joins five of the six tables into `staffing_outlook` | **Transformations** |
| Data app | the grid | **Apps** |
| Flow | runs all of it, in order, every morning | **Flows** |

In **Storage**: two `in.c-` buckets named after the connector and the configuration ID
(`keboola-ex-http-…`), and one `out.c-Boolabean-staffing-outlook` bucket.

## The one number that proves the join

`staffing_outlook` should hold **exactly 42 rows**: six cafés times the seven days in the forecast.

- **More than 42:** an input has duplicate rows, such as the forecast loaded twice with incremental
  load on, or a café listed twice in `stores`. The joins cannot multiply rows on their own.
- **Fewer:** a join dropped rows, such as a `location_id` that did not map onto a `store_id`, or a
  forecast with fewer than seven days.
- **Ten columns,** and `short_handed` true on a **few** rows: never all of them, rarely none.

<details>
<summary>Which columns may be empty, and which may not</summary>

Open the table's **Data Sample** and check the columns the right way round. `store_name`, `city`,
`date`, `weekday`, the two forecast columns and `rostered_staff` are filled on **every** row; they
come from straight lookups. `expected_units` and `expected_units_per_person` can be empty on a
row, and that is not an error: it means the summer never had a day in that café's weather band, so
there is no history to average. In this sample the band with no history is *cold and dry*: five of
the six cafés never saw a dry day under 18 °C all summer, while cold, wet days happened everywhere.
Our week had four `short_handed` rows, and a cool, wet week can flag nothing, in which case the
grid is right to be all quiet.

So the failure signals are the extremes: a lookup column empty on any row means a join matched
nothing, and `expected_units` empty on *every* row means the two band expressions in the SQL no
longer match each other.

</details>

## Reading a flow run

The flow's **All Runs** tab lists every run: who or what started it (your name, or
`Schedule for <flow ID> Scheduler` for a scheduled run), duration and status. Expand a run to see its phases.

![Screenshot - All runs](/getting-started/check/09-all-runs.png)

- **Success** is the goal: a few minutes end to end, about two for the loads, under one for the
  transformation, most of it for the app deploy.
- **Error is not all lost.** Phases run in order, so the earlier ones finished and their tables
  are updated; our first run failed at the app phase with `staffing_outlook` already rebuilt.
- **More jobs than tasks is normal:** one per task, a **Conditional Flows phase** job per phase, a
  **Conditional Flows** job for the run, and one per row for a row-based connector (six lines for
  the five-file configuration).

:::tip[Let Kai read the run for you]
```text title="Prompt" wrap
My flow run failed. Which task failed, and why?
```
Kai reads the run's job logs, which is faster than expanding them one at a time. The same question
from a terminal is `kbagent kai ask --project <alias> -m "…"`.

## The same checks from a terminal

Every number above has a read-only command behind it, which is the fastest way to answer "did last
night's run work?" without opening the project. They need
[kbagent](/cli/getting-started/) connected to your project. `docs-demo` below is a project alias,
substitute yours:

```bash
kbagent job list --project docs-demo --component-id keboola.flow --limit 5
```

```bash
kbagent job detail --project docs-demo --job-id <job-id>
```

```bash
kbagent storage tables --project docs-demo --bucket-id out.c-Boolabean-staffing-outlook
```

Recent runs with status and duration; one run, including which task failed; and the row count that
proves the join. None of them changes anything.

## The failures that actually happen

<details>
<summary>The transformation fails inside the flow, but works on its own</summary>

Its phase is running before the loads finish. Check that both connectors sit in an *earlier*
phase, not the same one.

</details>

<details>
<summary>Every task succeeds, but the grid is unchanged</summary>

The app phase is missing from the flow, or the app was never deployed after it was published, so
it still serves the old table. Read the run detail top to bottom: the phases run in the order
shown, and an app that is not in the flow is not refreshed by it.

</details>

<details>
<summary>The app phase fails, and the rest succeeds</summary>

A deploy builds and starts a container, and it can fail for reasons that have nothing to do with
your data. The table is already rebuilt; open the app's page and start it again from there. The
job's own error is usually uninformative.
[Put it in front of someone](/getting-started/app/#if-it-goes-wrong) shows how to read the
container's startup log, which is where the reason actually is. After several failed starts the
platform disables the app (a banner says it failed to start automatically multiple times, and the
button reads **Start App**), and the flow's app phase will keep failing until someone starts it by
hand. If the error repeats, that is one for [Support](/management/support/) with the job link.

</details>

<details>
<summary>The forecast table has 42 rows, but the outlook has more</summary>

Duplicate input rows: see the one number above.

</details>

<details>
<summary>The scheduled run never happens</summary>

The schedule was saved but the flow is disabled, or the project is out of runtime credits.

<details>
<summary>Jobs queue instead of running</summary>

Too many parallel tasks in one phase. Ten concurrent component jobs is the
[recommended ceiling](/flows/); Support can adjust a project's limits. Split the phase.

</details>
