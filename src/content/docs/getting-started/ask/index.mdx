## Reading is different from building

- **Here Kai reads what you built** instead of building for you. Querying a table and calculating a
  metric is [Data Exploration](/kai/use-cases/#data-exploration), and it needs nothing set up.
- **Nothing on this page changes the project.** Kai's read-only tools run without asking by
  default, so expect an answer, not an approval card, unless this project's
  [tool permissions](/kai/settings/#tool-permissions) are set to ask.

## Ask it

<Tabs syncKey="howto">
<TabItem label="Prompt">

:::tip[The question the guide started with]
```text title="Prompt" wrap
Using staffing_outlook: which café is short-handed on which day next week, and what in the forecast makes that day different from the rest of its week?
```

**Check:** Kai names the flagged café-days (the rows where `short_handed` is true) and, for each,
what sets that day apart from the rest of its week, with the table's figures. Usually it is a warm,
dry forecast on a thin roster. When the forecast is much the same all week, Kai names the roster as
the difference instead. In a week under 18 °C Kai will tell you nobody is short-handed, and that is
the table being right: the sample's history is one summer, and on a cold day it never puts more
than 65.5 units on one person.
:::

The same table answers what-if questions too:

```text title="Prompt" wrap
Using staffing_outlook: if one extra person joined the roster on every short-handed day, which of those days would still be over 67 expected units per person, and what would each day's figure become?
```

**Check:** Kai recomputes the per-person figure for every flagged row with one more person and
lists the before and after. In a week with nothing flagged there is nothing to recompute.

<details>
<summary>What Kai answered on the day this was written</summary>

The answer changes with the forecast. In the week of the screenshots, 1 to 7 October 2026, three
café-days were flagged: Vinohrady on Thursday, its warmest day, and Zelný trh on Monday and
Tuesday, where Kai noticed that the forecast was much like its other days' and the roster was
two people instead of three, *"a roster fix, not a forecast surprise"*.

The follow-up's answer that week was *none of them*: one extra person brought the three days to
54.8, 56.8 and 56.8 expected units per person. That is the kind of thing nobody can see in five separate files, and it took
one question because the pipeline had already put the roster next to the demand.

</details>

<details>
<summary>If the numbers come out different</summary>

Kai wrote its own SQL and may have drawn the lines somewhere else: rounded before dividing, or read
`short_handed` as text. The definitions this guide uses are the columns your transformation
already wrote, so point Kai at those (`expected_units`, `rostered_staff`,
`expected_units_per_person`) rather than re-prompting blind. To see where its lines are, ask in the
same chat:

```text title="Follow-up prompt" wrap
Show me the SQL you ran for that answer and the rows it is based on.
```

It only reads, so by default it asks for no approval, and a wrong filter or a wrong table is easier
to spot in the SQL than in the prose.

<TabItem label="UI">

There is no dialog for "answer this question". Reading a table by hand means querying it. Open a
[workspace](/getting-started/transform/workspace/) on the same table and run the SQL yourself, in
your project's dialect.

**If your project uses Snowflake**

```sql
SELECT "store_name", "city", "date", "weekday", "expected_units", "rostered_staff",
       "expected_units_per_person"
FROM "staffing_outlook"
WHERE "short_handed" = TRUE
ORDER BY "expected_units_per_person" DESC;
```

The follow-up is the same query with one more person on the roster:

```sql
SELECT "store_name", "date",
       ROUND("expected_units" / ("rostered_staff" + 1), 1) AS "with_one_more"
FROM "staffing_outlook"
WHERE "short_handed" = TRUE
ORDER BY "with_one_more" DESC;
```

If those raise `invalid identifier`, your table has upper-case column names: Snowflake upper-cases
an alias that was not quoted, and the **Prompt** path's Kai does not quote them. Either drop the
quotes from the query or upper-case the names inside them. The
[transform page](/getting-started/transform/#if-it-goes-wrong) explains why the two cases exist.

**If your project uses BigQuery**

BigQuery reads double quotes as text rather than as names, so the same two queries go without
them, with `date` in backticks as on the transform page:

```sql
SELECT store_name, city, `date`, weekday, expected_units, rostered_staff,
       expected_units_per_person
FROM staffing_outlook
WHERE short_handed = TRUE
ORDER BY expected_units_per_person DESC;
```

```sql
SELECT store_name, `date`,
       ROUND(expected_units / (rostered_staff + 1), 1) AS with_one_more
FROM staffing_outlook
WHERE short_handed = TRUE
ORDER BY with_one_more DESC;
```

<TabItem label="CLI / API">

`kbagent kai ask` puts the same question from a terminal and prints the answer, tables and all. It
is one shot: no chat to keep, nothing created. It needs kbagent connected through
`kbagent project add` with an admin (master) token; a connection made with `kbagent auth login`
does not reach Kai.

```bash
kbagent kai ask --project docs-demo -m "Using out.c-Boolabean-staffing-outlook.staffing_outlook, which cafe and day has the highest expected units per person, and how many rows are flagged short_handed?"
```

Name the table by its full Storage ID rather than the short name the transformation used: the
short name only exists inside a transformation's input mapping.

For a conversation rather than a single question, `kbagent kai chat -m "…"` returns a chat ID and
`--chat-id` continues it.

**Check:** the answer names a café and a day: the top row of `staffing_outlook` sorted by
`expected_units_per_person`, descending. If you would rather have the numbers than the prose,
`kbagent storage table-detail --project docs-demo --table-id out.c-Boolabean-staffing-outlook.staffing_outlook`
gives you the shape of the table and
[a workspace](/getting-started/transform/workspace/) gives you the SQL.

</TabItem>

## The same request, as one prompt

You built this one step at a time so every result stayed checkable. Once you have seen the
pieces, the loading, the forecast and the joining are one request rather than three:

```text title="Prompt" wrap
Load the five CSV files at https://help.keboola.com/getting-started/boolabean/ (stores, products, sales, staffing, weather_daily) into Storage as one HTTP data source configuration. Add a second HTTP configuration for the open-meteo forecast CSV for the six cafés. Then build a transformation that joins them into staffing_outlook, one row per café per forecast day with expected units per rostered person and a short_handed flag over 67, and tell me which café and day come out most stretched.
```

Two things to know before you paste it:

- **It is still a dozen approvals, not one.** Kai asks before each change it makes.
- **Kai tends to stop after the first part,** answering *"I'll tackle this in stages"* and waiting
  for *continue*. In our runs the same work as four prompts in one chat needed no nudging.

The one-prompt version works, and it is the faster route once you have seen the pieces separately.
{/* Measured: 2026-09-03 and 2026-09-08, a four-part prompt stopped after stage one both times;
the four-prompt version ran to the end in 14 minutes with 12 approvals and 0 nudges (DECISIONS.md,
2026-09-08). The exact one-prompt wording above has not itself been run since the dataset
